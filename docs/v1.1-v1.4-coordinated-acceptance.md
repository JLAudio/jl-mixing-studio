# JL Mixing Studio v1.1 / Automation v1.4 coordinated acceptance matrix

Status: **Planned / pre-RC**

Target releases:

- JL Mixing Automation `v1.4.0`
- JL Mixing Studio `v1.1.0`
- Certified integration baseline: Studio `v1.1.0` with Automation `v1.4.0`
- Automation API contract: `1.0`

This document is the coordinated acceptance source of truth for the paired release. It is intentionally focused on validating the completed Automation API integration and behavior-preserving Studio refactor. New Studio workflow features and broader UI redesign are outside this release acceptance scope.

## Release intent

Automation v1.4.0 provides the released Automation API 1.0 provider contract and structured workflow capabilities consumed by Studio.

Studio v1.1.0 adopts Automation API 1.0, completes the internal Rust/frontend maintainability refactors, and preserves the existing Studio workflow feature set.

The acceptance question is therefore:

> Does the refactored Studio v1.1 RC, using the Automation v1.4 RC through API 1.0, preserve the existing supported Studio workflows and safety behavior without regression?

## Scope freeze

In scope:

- Automation API 1.0 discovery and capability reporting;
- Studio compatibility/version/capability handling;
- Studio setup;
- client creation;
- project creation;
- intake validation and report display;
- revision creation;
- revision approval;
- delivery creation, overwrite, clean replacement, ZIP creation, and Delivery Notes;
- reports/files/metadata presentation;
- Copy Path and Open Folder actions;
- settings and diagnostic behavior;
- behavior after missing/incompatible Automation;
- uncertain/no-retry behavior and destructive-operation safeguards;
- packaged install, upgrade, uninstall, and settings persistence where applicable.

Out of scope for v1.1 acceptance:

- newly exposing Automation options not already present in Studio v1.0;
- broad UI/wireframe redesign;
- new Automation API capabilities beyond the approved v1.4/API 1.0 provider contract;
- native Windows Automation execution;
- signing/notarization;
- DAW template management;
- localization;
- unrelated feature work.

## Result values

Use one of:

- `Pass`
- `Fail`
- `Blocked`
- `Not applicable`
- `Deferred`
- `Not run`

Every `Fail` or unexpected `Blocked` result must reference a GitHub issue before the RC can be approved.

## Windows scope

JL Mixing Automation is not natively supported on Windows in this release plan. Windows Studio acceptance therefore verifies packaging, launch, rendering, settings, navigation, safe standalone behavior, and graceful Automation-unavailable diagnostics. Automation-backed workflow execution is not required on Windows and is not a release defect.

## Apple Silicon scope

CI must continue compiling the Apple Silicon target. Manual packaged acceptance should be performed if suitable hardware is available. If hardware remains unavailable, record the platform as `Deferred` rather than implying it was user-verified.

## RC defect policy

During RC acceptance:

- fix release blockers and genuine regressions only;
- do not add newly exposed Automation features;
- do not redesign the UI;
- do not opportunistically refactor unrelated code;
- repeat affected tests after every RC fix;
- create a new RC rather than moving/reusing a published RC tag.

A defect is release-blocking when it materially breaks an existing supported Studio workflow, violates Automation API 1.0 compatibility, weakens destructive-operation/no-retry safety, corrupts or loses user data, prevents supported installation/launch, or causes a required release gate to fail.

## Final coordinated release decision

The paired release may proceed only when:

- [ ] Automation v1.4 required release gates pass.
- [ ] Studio v1.1 required automated gates pass.
- [ ] The certified Studio/Automation API 1.0 integration matrix passes on the primary supported Automation platform.
- [ ] The existing Studio end-to-end workflow passes against the Automation v1.4 RC.
- [ ] Refactor-focused UI regression checks pass.
- [ ] Packaged Intel macOS acceptance passes.
- [ ] Windows x64 passes its defined limited scope.
- [ ] Apple Silicon is either manually accepted or explicitly recorded as deferred.
- [ ] Every failed or unexpectedly blocked test has a tracked issue and no release-blocking defect remains open.
- [ ] RC versions/commits and tester evidence are recorded above.
- [ ] Final Automation v1.4.0 and Studio v1.1.0 release tags are created only after explicit release approval.
